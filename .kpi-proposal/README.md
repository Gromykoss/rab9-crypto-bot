# rab9 KPI/E2E — предложение (черновик от оператора)

> Подготовлено оператором Hermes 15.08.2026 в ответ на MGT_maccha аудит:
> «rab9 без KPI/E2E — единственный слепой проект».

## Диагноз

Инфраструктура **здорова**: оба сервиса active, Core PID жив, HTTP :8089 ок,
listener жив, offset свежий. «Слепота» = **19 дней без входных сигналов** (мемы
молчат — рыночное затишье, не сбой) + **отсутствие бизнес-метрик**.

`loop_verifier.py` проверяет только **качество** сигнала (4 тех-чека:
number_accuracy, verdict_consistency, cabal_correctness, synthesis_quality),
но ни одна метрика не отвечает на вопрос «а есть ли от этого результат?».

`loop_state.json` показывает: 37 analyses, 0 duplicates — и **0 закрытых сделок**.

## Что предлагается — 5 слоёв KPI

| Слой | Метрика | Где брать |
|------|---------|-----------|
| **Вход** | сигналов/день, уникальных токенов | `data/rab9_trades.db` + `loop_state.json` |
| **Конверсия** | сигнал → валидный трейд → закрытая позиция | trades DB |
| **Результат** | реализованный PnL, win-rate, средн. hold | trades DB |
| **Качество** | средний score loop_verifier (PASS/FLAG/FAIL) | `loop_state.json` (уже есть) |
| **E2E health** | offset двигается? сервисы active? сигнал → возврат в БД за N мин | `msf_offset.txt` + systemd |

## Файлы

- `kpi_report.py` — скелет-спецификация (метки `# TODO(profile)` и `...` там,
  где нужно вписать реальные имена таблиц/полей rab9_trades.db).

## Не делать

- ⛔ Не запускать `kpi_report.py` из этого каталога напрямую — это спецификация,
  не рабочий скрипт (местами заглушки `...`).
- ⛔ Не коммитить в production без проверки реальной схемы `rab9_trades.db`.

## Следующие шаги (для профиля rab9)

1. Прочитать реальную схему: `sqlite3 data/rab9_trades.db ".schema"`.
2. Заполнить `kpi_input/conversion/result` реальными запросами.
3. Определить порог аномалий (когда печатать в stdout — например,
   offset_stale или конверсия застряла на 0 при живом входе).
4. Подключить к ночному cron (silent-by-default, по образцу `burnie_cron.sh`).
