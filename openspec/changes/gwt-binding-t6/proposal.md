# Change: gwt-binding-t6 — GWT-биндинг пяти доменов (закрытие отложенного T6)

Статус: в работе (19.11.2026). Автор: RAB9 (rab9). База: main `03c9a01`.

## Проблема

Пять FROZEN-спек (`pumpportal-ingress` v0.3, `wallet-watch` v1.0, `accumulation-radar` v1.0,
`analysis-filters` v1.1, `standalone-analyzer` v1.2) описывают поведение домена сценариями в
prose-форме `#### Scenario: <имя>` + строки GIVEN/WHEN/THEN. У сценариев нет id, у тестов нет
маркеров `@pytest.mark.scenario`, в `.ci/scenario_map.yaml` домены отсутствуют. В итоге:

* 46 сценариев не участвуют в трёхсторонней сверке «карта ↔ карточка ↔ тест»;
* job `scenarios` не может выбрать тесты по изменённым файлам для этих доменов
  (изменение кода домена не запускает его сценарные тесты);
* линтер `lint-cards` падал на этих же сценариях (92 ошибки) — красный CI на любом
  пуше, задевающем `paths`-фильтр workflow (снято 19.11 правкой линтера, коммит `eb14688`);
* автотесты у двух доменов уже есть (`tests/test_pumpportal_listener.py`,
  `tests/test_standalone_analyzer.py`), но не связаны со сценариями — связь живёт только
  в docstring'ах.

Причина отложения зафиксирована в самом `check_scenario_map.py`: «GWT-binding домена — на
закрытии фичи 2 (T6)». Фича 2 закрыта, T6 остался долгом.

## Зачем сейчас

Долг перестал быть теоретическим: он дал красный CI и он же делает бесполезным job `scenarios`
для четырёх из пяти доменов (изменение `analyzer_main.py`/`pumpportal_listener.py` не
подтягивает их сценарные тесты). Пока биндинга нет, регрессия в радаре/машине состояний
может уехать в main при зелёном CI.

## Скоуп

1. В каждой из пяти FROZEN-спек: заголовок сценария переводится в карточную форму
   `#### <имя сценария> — GIVEN <условие> \`<домен>.<id>\``, строки WHEN/THEN становятся
   пунктами `- WHEN` / `- THEN`. Текст GIVEN/WHEN/THEN и имена сценариев сохраняются дословно.
2. Каждая спека получает v-бамп (v0.3→v0.4, v1.0→v1.1, v1.0→v1.1, v1.1→v1.2, v1.2→v1.3) с
   записью в таблице фризов `openspec/project.md` и строкой delta в шапке спеки.
3. `tests/test_<домен>_gwt.py` — по одному pytest-тесту на сценарий, каждый помечен
   `@pytest.mark.scenario("<id>")`; тесты герметичны (tmp_path, без сети).
4. `.ci/scenario_map.yaml` — по записи на сценарий: `card` / `test` / `code`.
5. Из `WHITELIST` в `.ci/check_scenario_map.py` убираются строки, которые больше не нужны
   (код и тесты домена теперь в карте), чтобы whitelist отражал реальность.

## Вне скоупа

* Изменение поведения доменов: биндинг не меняет ни одну строку продакшн-логики.
  Поведенческих дельт (`-delta.md`) по этой причине не создаётся — правило шага 4 CDD
  (дельта при смене поведения) не срабатывает.
* Реализация отсутствующих сценариев: если сценарий нельзя связать с существующим кодом
  честным тестом, он остаётся prose-сценарием (линтер пропускает prose-класс с
  предупреждением) и попадает в отчёт как открытый пункт, а не закрывается заглушкой.
* `llm-intel` (уже связан, 6 сценариев) и легаси-домены вне пяти спек.

## Критерий готовности

* `python3 .ci/lint_gwt_cards.py openspec/specs --tests tests/` — 0 ошибок;
* `python3 .ci/check_scenario_map.py --base <base>` — «scenario map completeness OK»
  без mismatch'ей (карта = карточки = тесты);
* `./venv/bin/python -m pytest tests/ -q` — зелёный;
* прогон workflow `gwt` на main — все три job'а зелёные;
* отчёт: сколько из 46 сценариев связано, какие остались и почему.

## Риски

* Тест, «подогнанный» под код, вреднее отсутствия теста → каждый тест проверяет THEN из
  текста спеки, а не внутреннее состояние; слабые тесты (нет вызова продакшн-функции,
  assert без наблюдаемого эффекта) не принимаются.
* v-бамп пяти FROZEN-спек — ручная правка замороженных артефактов: обязателен reconcile
  (текст сценариев не меняется, меняется только форма карточки) и запись в таблице фризов.
